# 이사 실행 매니저: 준비부터 당일까지 놓치지 않게 돕는 멀티에이전트

## 1. 한 줄 제안

이사 날짜·물품·예약 현황을 입력하면 **지금 해야 할 3가지와 아직 확정되지 않은 일**을 보여주고, 함께 이사하는 사람과 담당자를 나눠 진행 상황을 관리하는 서비스다. 단순 체크리스트 생성이 아니라 예약 상태와 일정 변경을 계속 추적하는 ‘이사 실행 보드’를 지향한다.

이사는 용달을 예약했어도 에어컨 철거 날짜가 맞지 않거나, 팔기로 한 책상이 당일까지 남거나, 인터넷 이전 신청을 잊기 쉽다. 이 서비스는 누락과 일정 충돌을 줄이는 데 집중한다. 사용자 대신 예약·해지·신고를 완료했다고 주장하지 않는다.

## 2. 누가 왜 다시 방문할까?

첫 사용자층은 결혼·독립·전세 만료 등으로 여러 일을 동시에 챙기는 1~2인 가구다. 특히 두 사람이 업무를 나눠 맡는 이사에서 가치를 검증한다.

| 일반 체크리스트 | 이 서비스의 목표 |
| --- | --- |
| 모든 항목을 한꺼번에 나열 | 사용자 상황에 맞는 항목과 ‘오늘 할 일 3개’만 우선 제시 |
| 체크하면 끝 | 문의 중·예약 확정·완료를 구분하고 담당자와 확인 메모를 남김 |
| 날짜가 바뀌어도 목록이 그대로 | 이사일 변경 시 영향을 받는 예약을 ‘재확인 필요’로 표시 |
| 신청처를 다시 검색 | 가능한 경우 출처가 있는 공식 안내·신청 경로를 연결 |

첫 방문에서는 이사 날짜, 출발·도착 지역, 이사 방식, 큰 물품, 이미 예약한 일을 짧게 입력한다. 상세 주소는 초기 계획 생성에 요구하지 않는다. 시스템은 누락된 핵심 정보만 추가로 묻고 바로 실행 보드를 보여준다. ‘3분 안에 첫 계획 생성’은 제품 목표이지 검증된 성능이 아니다.

## 3. 실제 사용 시나리오

두 사람이 10월 말에 이사한다. 책과 에어컨은 가져가고 책상은 판매할 예정이다. 용달·에어컨 철거·인터넷 이전은 아직 예약하지 않았다.

1. 사용자가 날짜·지역·물품·예약 상태를 입력한다. 서비스는 “책상 판매 인도일은?”, “에어컨 철거 담당은?”, “인터넷은 이전인가 해지인가?”처럼 계획에 필요한 미결정 사항을 확인한다.
2. 보드 상단에는 ‘오늘 할 일 3개’가 나온다. 예: 용달 가능일 문의, 에어컨 철거 일정 확인, 인터넷 이전 가능일 조회. 각 작업에는 담당자·상태·관련 경로가 붙는다.
3. 용달에 문의만 했으면 ‘문의 중’이다. 사용자가 확정 날짜와 예약번호 또는 메모를 기록해야 ‘사용자 확인상 확정’이 된다. 외부 업체가 검증한 상태로 표현하지 않는다.
4. 이사일이 바뀌면 기존 예약은 자동으로 새 날짜에 맞춰졌다고 보지 않는다. 관련 작업을 ‘재확인 필요’로 바꿔 담당자에게 다시 확인하도록 보여준다.
5. 이사 당일에는 운반·판매·처분 물품을 구분하고, 이후에는 전입신고·전기 정산 등 남은 일을 보여준다.

사용자가 계획을 한 번 보고 떠나는 것이 아니라, 예약 상태가 바뀌거나 일정이 바뀔 때 다시 열어볼 이유를 만드는 것이 핵심이다. 다만 이사는 저빈도 사건이므로 장기 구독을 전제로 하지 않는다.

## 4. 초기 서비스 범위

| 영역 | 입력·확인할 것 | 사용자에게 돌려줄 행동 |
| --- | --- | --- |
| 물품 | 가져감·판매·처분·미정, 큰 물품 | 운반·판매·처분 작업 분리 |
| 운반 | 용달/이사업체 문의·예약 확정, 차량·엘리베이터 조건 | 미확정 예약과 날짜 충돌 표시 |
| 설치 가전 | 에어컨 철거·재설치 필요 여부와 담당자 | 철거→운반→재설치 선후관계 표시 |
| 통신·공과금 | 인터넷 이전/해지, 도시가스 전출·전입, 전기 정산 | 해당 여부 확인과 공식 안내 연결 |
| 입주 후 | 전입신고와 주소 변경 | 이사 후 남은 일 표시 |

[정부24](https://www.gov.kr/portal/main)의 전입신고, [한국전력의 이사 전 사용량 정산 안내](https://home.kepco.co.kr/kepco/front/html/CY/H/A/CYHAHP001.html), [폐가전 무상방문수거의 수거 기준](https://www.15990903.or.kr/portal/cnts/selectContents.do?cntnts_id=A1000005)처럼 출처가 있는 안내를 우선 활용한다. 지역·계약·업체마다 절차와 처리 기간이 다르므로 출처와 확인일을 표시하며 획일적 마감일·비용을 사실처럼 제시하지 않는다. 예약·신고·결제 대행과 날씨 조회는 초기 범위 밖이다.

## 5. Agent → Contract → Orchestration

핵심은 LLM을 세 번 호출하는 것이 아니라 **사용자 사실 보존 → 필요한 행동 생성 → 검증된 행동의 일정화**다. 전체 실행과 실패 중단은 Supervisor가 관리한다.

| 순서 | Worker | 한 가지 책임 | Output Contract |
| --- | --- | --- | --- |
| 1 | move_scope_agent | 물품·서비스·예약 상태와 미결정 사항 정리 | MoveScopeResult |
| 2 | move_action_agent | 각 대상의 작업·선행 조건·확인 사항 생성 | MoveActionPlanResult |
| 3 | move_timeline_agent | 이사일과 선행 조건에 맞춰 작업 배치·우선순위 결정 | MoveTimelineResult |

예를 들어 첫 Worker가 ‘책상=판매 예정’을 반환하면 이를 검증한 뒤 둘째 Worker가 ‘판매 글 올리기·인도일 확정’을 만든다. 셋째 Worker는 이를 이사 전 작업에 놓는다. ‘책상 운반’처럼 앞 단계와 충돌하는 작업은 구조화된 작업 종류와 대상 ID로 검증한다. 자유문장만 보고 확정할 수 없는 판단은 사용자 확인 항목으로 남긴다.

~~~text
사용자 입력
 → Supervisor → 범위 Worker → MoveScopeResult 검증
 → Supervisor → 행동 Worker → MoveActionPlanResult 검증
 → Supervisor → 일정 Worker → MoveTimelineResult 검증
 → 오늘 할 일·미확정 예약·전체 일정 표시
~~~

검증에 실패하면 뒤 Worker는 실행하지 않는다. 오류 단계와 이유를 보여주고 사용자가 입력 또는 생성 결과를 수정할 경로를 제공한다. 사용자가 상태·날짜를 바꾸면 영향을 받는 결과를 다시 계산한다. **현재 수업용 코드는 정해진 3-Worker 순서와 ID 누락 검증까지 구현한 실습**이며, 상태 변경에 따른 선택적 재실행은 제품 단계의 추가 설계다.

## 6. Output Contract에서 무엇을 검증할까?

Pydantic은 필수 필드·타입·상태값을 검사하고, Orchestrator의 Python 로직은 단계 간 의미 관계를 검사한다.

| 계약 | 필요한 데이터 | 의미 검증 |
| --- | --- | --- |
| MoveScopeResult | 원본 item_id/service_id, 구분, 사용자 상태, 미결정 사항 | 입력 대상 누락·중복 금지, 말하지 않은 예약 확정 금지 |
| MoveActionPlanResult | 대상 ID별 task_id, 작업 종류, 선행 작업, 확인 필요 여부 | 없는 대상에 작업 금지, 모든 대상에 작업 또는 ‘추가 작업 없음’ 이유 필요, 판매 대상 운반 같은 명시적 충돌 금지 |
| MoveTimelineResult | task_id별 전·당일·후 단계, 선행 관계, 우선 작업, 확인 필요 목록 | 모든 작업 한 번씩 포함, 선행 작업보다 앞에 배치 금지, 완료 근거 없는 작업 완료 표시 금지 |

구체적 필드명과 상태 enum은 기존 Pydantic 계약과 맞춘다. 지역 규칙·법적 기한·업체 가용성을 LLM이 만들어내지 못하게, 출처 없는 날짜 제안은 ‘확인 필요’로 구분한다. 예약번호·메모는 사용자가 기록한 정보이지 외부 검증 결과가 아니다.

## 7. 사용자 화면과 재방문 흐름

최소 화면은 세 개다.

1. **시작하기**: 이사 날짜·지역·물품·예약 현황을 짧은 질문으로 입력.
2. **내 이사 보드**: 오늘 할 일 3개, 미확정 예약, 날짜 충돌, 담당자별 할 일 표시. 카드에서 안내 경로를 열고 상태·메모를 변경.
3. **전체 일정**: 이사 전·당일·후의 작업과 남은 일 표시. 날짜·물품 결정 변경 후 재계산 결과 확인.

상태는 ‘미시작 → 문의/신청 중 → 사용자 확인상 확정 → 완료’로 구분하고, 변경으로 확인이 무효해지면 ‘재확인 필요’를 별도로 표시한다. 동거인 공유는 유용하지만 링크만으로 주소·연락처가 노출되지 않도록 권한·만료·철회를 설계해야 한다.

## 8. 구현 단계와 현재 코드의 위치

| 단계 | 산출물 | 상태 |
| --- | --- | --- |
| 수업용 개념 증명 | 세 Worker, Supervisor 결정, Pydantic 계약, 대상 ID 검증, Trace | 08_my_orchestration.py와 my_worker_definiitons.yaml에 있음 |
| 사용 가능한 MVP | 입력 API, 저장되는 보드, 상태·담당자 변경, 오늘 할 일, 날짜 변경 재계산, 출처 있는 안내 | 미구현 |
| 상용화 검증 | 알림, 안전한 공유, 출처 갱신 운영, 오류·문의 대응, 개인정보·보안 검토, 사용자 실험 | 계획 단계 |
| 외부 연동 | 견적·예약·확인 상태 연동, 결제 또는 제휴 | 제휴·권한·동의 확보 후 검토 |

기존 mini_multi_agent_02_role_task_contract에 붙일 때는 Agent Registry·Runtime과 naming/import 구조를 재사용한다. Output Contract를 기존 schema 구조에 맞춰 등록하고 orchestration에 Supervisor 루프와 검증을 둔다. routers/contracts.py의 기존 /api prefix 아래에 POST /runs/moving-flow를 추가해 Swagger에서 정상·입력 오류·계약 실패·Tool 실패를 테스트한다. **독립 수업 스크립트를 실행한다고 해당 URL이나 이사 보드가 생기는 것은 아니다.** API 구현과 사용자용 서비스 구현은 별도 단계다.

MCP Tool은 공식 안내 또는 지역별 정보 조회가 실제로 필요할 때 붙인다. 외부 조회가 실패하면 내용을 지어내지 않고 ‘공식 안내 확인 불가’와 수동 확인 경로를 반환한다.

## 9. 사람들이 실제 쓸지 검증하는 방법

이사 예정자 10~20명의 기존 준비 방식을 인터뷰하고, 5명 이상에게 입력부터 오늘 할 일까지 직접 써보게 한다. 확인할 질문은 다음과 같다.

- 첫 화면에서 다음 행동을 1분 안에 이해하는가?
- 계획 생성 후 예약 상태를 갱신하려고 다시 방문하는가?
- 잊고 있던 예약·처분 작업을 실제로 발견하는가?
- 날짜 변경 후 재확인 목록이 도움이 되는가?
- 두 사람이 담당자 나누기를 실제로 사용하는가?

계획 생성 완료율, 첫 작업 실행률, 예약 상태 갱신률, 7일 내 재방문율, 이사일까지 미확정 작업 수를 본다. 이사 후에는 “서비스 덕분에 놓치지 않은 일이 있었는가?”를 묻는다. 기본 보드는 무료로 두고 제휴 견적·예약 연결 또는 부동산/이사업체 제공형을 **사업 가설**로 검토한다. 광고·수수료가 붙는 추천은 명확히 표시하고 추천의 공정성을 검토한다. 장기 월 구독은 이사 빈도가 낮아 초기 기본 모델로 삼지 않는다.

## 10. 제출용 결론

이 프로젝트는 ‘이사 체크리스트를 만들어주는 챗봇’이 아니라 **이사 중 결정·예약·실행 상태가 끊기지 않도록 돕는 보드**를 지향한다. 수업 과제에서는 Supervisor → Worker → Output Contract 검증을 먼저 완성하고, 실제 사용성은 상태 저장·재계산·담당자 공유·출처 관리로 확장한다. 가장 먼저 검증할 가치는 “사용자가 오늘 할 일을 알게 되고 예약 누락을 줄일 수 있는가”이다.
